# Cold Call Guide — outcome tracker

Each item below preserves a distinct required project outcome. Items are marked complete only where implementation evidence is present.

## 1. Live Call Guide and eight-stage workflow
- [x] **A caller can work through the eight cold-call stages in order.** Show one stage at a time with its stage number and purpose. The stages are: (1) Opening — reach the correct person and introduce the caller; handle receptionists, wrong numbers, and busy people. (2) Purpose — explain why calling in clear, simple language; handle questions about the company or how the number was obtained. (3) Permission — establish whether the prospect can talk now, wants a callback, or would prefer to end the conversation. (4) Their business — understand what the prospect’s company does before discussing the caller’s services. (5) Their need, in their words — capture the prospect’s exact words about goals, challenges, or lack of need; this stage is especially important. (6) Objection — record why the prospect hesitates or refuses, including an existing provider, lack of interest, wrong contact, or request for information. (7) Next step — record the concrete agreement, such as a meeting, report, referral, or callback at a specific time. (8) Close — finish the call, record the outcome, preserve the prospect’s words, and save the call.

## 3. Save and end calls at any stage
- [x] **Call progress can be saved and ended early.** Provide Previous and Next Stage navigation and an End Call action available from every stage. The caller can end a call at any stage; do not force completion of all eight stages. The close operation saves the current/last stage, selected final outcome, agreed next step if captured, notes, exact words, and all prior saved stage results—even if the final stage has no text. Save the current-stage snapshot and outcome in one database transaction. An unchanged close retry with the same UUID idempotency key must replay safely without a duplicate; reusing the key with changed data must conflict. Preserve earlier stage notes instead of silently replacing them.

## 4. Call History and persistence
- [x] **Call History lists and opens saved calls.** Show the prospect, company, outcome, last stage reached, notes or summary, and timestamp. Opening a call shows its saved stage results and recorded prospect words. Saved calls and stage results persist after refresh.
- [x] **Supabase PostgreSQL stores the required records.** Provide `database/schema.sql` for two tables and the atomic write functions. `calls` includes a unique call ID, prospect name, company name, current/last stage, `in_progress` or `completed` status, final outcome, agreed next step if provided, latest note, start timestamp, end timestamp, and optional AI summary. `stage_results` includes a unique result ID, a reference to `calls.id`, stage number 1–8, event, exact prospect words, notes, optional close idempotency UUID, and record timestamp; repeated stage saves append records without overwriting earlier notes.

## 5. FastAPI contract
- [x] **The required API operations are implemented.** `GET /health` returns service status. `POST /calls` starts a call. `POST /calls/{id}/stages` saves a current-stage result atomically with the parent call update. `POST /calls/{id}/close` closes a call and records its final outcome; its request carries the current stage number, event, prospect words, notes, outcome, optional agreed next step, and a required UUID idempotency key so the final stage is saved even when blank. An unchanged retry with the same key is safe; changed data with a reused key returns a conflict. `GET /calls` lists prior calls. `GET /calls/{id}` retrieves one call and its stage results. Validate UUID path IDs and provide useful errors for these operations.

## 6. Optional post-call AI assistant
- [x] **The optional post-call AI assistant is useful but cannot block the core workflow.** Use only captured stage results, the prospect’s own words, the final outcome, and the agreed next step. Return a concise summary, the prospect’s stated need or objection, the agreed next step if any, and a suggested follow-up based only on what was actually agreed. Do not let the LLM navigate stages, turn a refusal into a positive lead, invent a meeting, or ignore a request not to be contacted. Use Gemini structured output only to select evidence IDs from a per-request allowlist; validate every returned ID and format displayed summary/follow-up text from the saved source fields rather than model-written prose. Make Gemini requests stateless with `store=False` and skip the provider entirely for `do_not_call` outcomes. Keep the provider key in Render environment variables, never frontend code or the repository. If the provider fails or its free quota runs out, calls still save and history still works.
